## 二、代价花在哪

**42/126 轮是协调开销**,分布很集中:

1. **最大一笔:test stage 的测试工装**(约一半开销)。38 条新用例的红 14→12→8→5→1,
   **没有一条是产品缺陷**(生产代码自 review APPROVE 后一个字节没动)。根因全部是
   「测试里的时间与异步」:fake timers 与轮询 API 互锁 / 数 flush 次数押注 promise 链深 /
   正负向断言用错等待方式 / mock 与模块级状态跨用例存活。
   → **已沉淀 RD-9..RD-14**。下个 Feature 写测试前读一遍,这部分开销大部分可省。
2. **两路核验排在实现 commit 之后**,各抓一条真问题,导致全量测试跑两遍、TECH/TC 改两轮。
   这是评审起效不是浪费,但若把第三方核验并进实现阶段的收尾自查,可省掉一次全量跑。
3. **子代理全程只发 idle 通知不发正文**(5 个 agent 无一例外),每轮都要追问或自己读落盘产物。
   宿主通道问题,非流程设计问题 —— 但它意外挡住了两次风险:一次是采信了跑到一半被截断的
   门禁日志(9 条假绿会混过去),一次是 AC-14 的旧语义断言(照它「修绿」= 把 BLOCKER 修复退回去)。

## 三、下次可以不一样的

- **测试工装先读 RD-9..RD-14**:这批的共同特征是**长得像通过** —— 产品 bug 会红,它们会绿。
- **第三方核验前移**到实现阶段收尾自查,而不是 commit 后另起一轮。
- **`state.json` 是 tracked 文件,而测试证据指纹含未提交 diff** —— `add-concern` 一写就打乱指纹,
  来回 commit/amend 两次才对齐。这是框架侧的摩擦,已在此留痕。
