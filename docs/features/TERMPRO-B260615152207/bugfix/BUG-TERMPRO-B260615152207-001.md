## 根因分析(深读代码 + 双路并行调查实证)

### 调查方法
两名 opus 子代理并行从两条独立通路深查(读真实源码 · 含 `node_modules` 内 addon 源):
1. **渲染通路**(WebGL/xterm 渲染)
2. **数据通路**(PTY → Host → IPC → renderer → term.write)

### 数据通路:已排除(~90% 置信)
| Hop | 类型 | 是否解码 | 位置 |
|---|---|---|---|
| node-pty → onData | JS `string`(已 UTF-8 解码) | 是 · node-pty 流式 `StringDecoder`(跨 chunk 缓冲半个多字节序列) | `node_modules/node-pty/lib/unixTerminal.js:64,93-95` |
| `ptyPool.proc.onData` | `string`(原样转发) | 否 | `src/host/ptyPool.ts:82,86,92` |
| protocol `pty:data` | `{ data: string; bytes: number }` | 否 | `src/shared/protocol.ts:134` |
| Host → renderer IPC | `string`,载于 `MessageChannelMain` **结构化克隆**(非 JSON/base64 · 绕过主进程) | 否 | `src/host/host.ts:88` · `src/main/main.ts:123-127` · `src/renderer/services/hostClient.ts:172,185-194` |
| `term.write(data)` | `string` | xterm 直接解析 | `src/renderer/terminal/terminalRegistry.ts:138` |

结论:全链路无任何点会把多字节 UTF-8 序列拆开独立解码,无 bytes↔string 有损往返。node-pty 的流式 `StringDecoder` 已在上游完成跨 chunk 重组,抵达 `term.write` 的始终是完整码点。**数据通路不是根因。**

### 相关代码(渲染通路 · 真因)
| 文件 | 行号 | 问题描述 |
|------|------|----------|
| `node_modules/@xterm/addon-webgl` `GlyphRenderer.ts` | 121-126 | `TextureAtlas.maxAtlasPages = min(32, gl.MAX_TEXTURE_IMAGE_UNITS)`(macOS 常为 ~16)· 静态字段 |
| `node_modules/@xterm/addon-webgl` `TextureAtlas.ts` | 150-205, 235-244 | 页数达上限 → `_mergePages`/`_deletePage`,**重排每个字形的 `texturePage` 索引** + 改页 `version`,置 `_requestClearModel=true` |

### 根因(真因 · 非症状)
WebGL 字形图集采用**分页纹理**(每页 512px,装满即开新页)。中文字符种类极多,CJK-heavy 会话很快把页数推到 `maxAtlasPages`(~16),触发 `_mergePages`/`_deletePage`:**合并/删页会重排所有字形的 `texturePage` 索引并改页 `version`**。GlyphRenderer 只在 version 变化时重绑「页→GL 纹理单元」,而**已绘制单元格的 `a_texpage` 属性与 texcoord 仍指向重排前的旧页**,直到一次全量 `_clearModel + _updateModel` 才修正。若重排发生后、全量重绘到位前(或后续只更新 `start..end` 局部行),单元格就会采样到**错误的纹理页 / 错误坐标** → 该格画出与码点不符的字形 = 错位/串字/错字。

- **DPR 无关**:此机制由「字形种类数」驱动,与像素比无关 → 这正解释了为何 0847660 的 DPR 修复治不了。
- **偶发被掩盖**:0847660 的 `clearTextureAtlas()` 在 DPR 事件时会顺手清空重置,短暂"修好",但字形数再涨又复发 → 用户感知为"仍然存在"。
- 已知同类问题:xterm.js #4480 / vscode #120129(代码注释 `WebglRenderer.ts:344-345` 亦引用)。

### 调用链路
```
CJK 输出持续 → 不同字形累积 → 图集页数达上限
  → TextureAtlas._createNewPage 触发 _mergePages/_deletePage(重排 texturePage 索引)
  → 已绘制单元格 a_texpage/texcoord 未与新图集同步
  → GlyphRenderer 采样错误纹理页 → 错字/串字(本 bug)
```

### 运行期需 dev/test 复核确认的点(de-risk)
1. 实跑日志确认抵达 `term.write` 的码点正确(活体排除数据通路):`terminalRegistry.ts:138` 处打印 `Array.from(data).map(c=>c.codePointAt(0).toString(16))` 对照 "中文测试"。
2. 关闭 WebGL(强制 DOM/canvas 渲染)A/B:相同正确码点下乱码消失 → 钉死在 WebGL 图集。
3. 监听 `webgl.onAddTextureAtlasCanvas`/`onRemoveTextureAtlasCanvas`:乱码出现与这些事件相关 → 确认分页合并根因。

## 修复方案(diagnose 阶段产出 · 🔴 用户确认后才进 dev · 本阶段不写 fix 码)

### 方案描述

**方案 A(推荐 · 根因修复):图集变更即重同步模型**
在 `TerminalView.tsx` 创建 `WebglAddon` 时,订阅其公开图集事件(已在 `@xterm/addon-webgl@0.19.0` typings 确认存在):
- `onRemoveTextureAtlasCanvas`(页合并/删除 = 索引重排时刻 · **关键**)
- `onAddTextureAtlasCanvas` / `onChangeTextureAtlas`(增页/换图集 · 兜底)

回调中强制**全量重绘模型**:`term.refresh(0, term.rows - 1)`(用微任务去抖,避免在事件回调里再触发图集变更造成重入)。这样每个单元格的 `texturePage` 索引在图集重排的同一帧被重建,采样到正确纹理页。订阅返回的 disposable 接入现有 active/tabId effect 的 cleanup(无泄漏)。

- **为何不直接 clearTextureAtlas**:在 add/remove 事件回调里调 `clearTextureAtlas()` 可能递归触发图集变更;`term.refresh` 仅重建模型、风险更低。dev 阶段二选一,以无重入 + 实测无残留为准。
- **取舍**:页合并是**低频**事件,触发一次全量 refresh 开销远小于持续乱码;不动渲染引擎选型、不降级到 DOM。

**可选硬化(scope 决策项 · 默认不纳入本 Bug)**
- 🔧 H1 · context-loss 自动重建:`onContextLoss` 现 dispose+null,但 active-effect 依赖 `[active,tabId]` 不变 → addon 不会自动重建(xterm core 会降级到 DOM 渲染,不会黑屏,但失去 WebGL 直到切 tab)。可在 context-loss 后触发重建。**不产生乱码**,属独立 robustness 缺口。
- 🔧 H2 · DPR 监听去冗余:0847660 的 `watchDevicePixelRatio` 与 xterm core 自带的 `ScreenDprMonitor`(resize+matchMedia · 更稳健)重叠且更弱。可移除自定义监听改依赖 core,或加 resize 兜底。**非本次乱码主因**,改动有回归面,建议另开。
