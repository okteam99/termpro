## 问题描述
**报告人**:用户(surongrongzz)

**问题描述**:
在 TermPro 终端里点击某些链接(例如 CLI 输出的预览地址 `http://localhost:56868/shell/close-install-confirmation`),会弹出一个原生确认框:

> Do you want to navigate to http://localhost:56868/shell/close-install-confirmation?
> WARNING: This link could potentially be dangerous
> [Cancel] [OK]

**期望行为**:
点击链接直接交给系统默认浏览器打开,不弹任何确认框(与纯文本 `http(s)` 链接的现有行为一致)。

**实际行为**:
弹确认框,需点 OK 才打开,且走 `window.open()` 而非系统浏览器。

**复现环境**:

- 链接类型:OSC 8 转义序列超链接(非纯文本 URL)

### 根因(真因 · 非症状)
OSC 8 超链接由 xterm **内置**的 `OscLinkProvider` 处理,而非 TermPro 自定义的 `SystemWebLinkProvider`。其链接激活逻辑(OscLinkProvider.ts:89)是:

```ts
activate: (e, text) => (linkHandler ? linkHandler.activate(e, text, range) : defaultActivate(e, text))
```

TermPro 创建 `Terminal` 时**没有传 `linkHandler` 选项**(terminalRegistry.ts:45),于是 OSC 链接点击落到 `defaultActivate` → 原生 `confirm()` 弹框 → `window.open()`。

为什么自定义的 `SystemWebLinkProvider`(它会把 http(s) 路由到 `openExternal`,无弹框)**救不了**这种链接:xterm 的 `Linkifier`(Linkifier.ts:175–198)按 **注册下标 = 优先级**(下标越小越优先)解析链接。`OscLinkProvider` 由 xterm 核心在构造时注册(下标 0),早于 `SystemWebLinkProvider`(下标 1)/`FsLinkProvider`(下标 2)。当一个 OSC 8 链接的可见文本恰好是 URL 时,两个 provider 都会命中同一批单元格,但**下标 0 的 OscLinkProvider 胜出**,自定义 provider 的链接被剔除。所以激活的永远是 OscLinkProvider 的 `activate` → 弹框。

这是**根因**,不是症状:`SystemWebLinkProvider`(terminalRegistry.ts 注释也写了"不要用 WebLinksAddon 默认 window.open 路径,否则可能弹确认框")只覆盖了纯文本链接这一路,**漏了 OSC 8 这条由核心 provider 占据的高优先级路径**。

### 调用链路
```
程序输出 OSC 8 转义序列(内嵌 URI)
  → xterm 解析 · cell 带 urlId 扩展属性
  → 用户点击
  → Linkifier 按 provider 下标解析:OscLinkProvider(下标0)胜出
  → OscLinkProvider.activate:linkHandler 未设 → defaultActivate
  → confirm("…could potentially be dangerous") → window.open()   ❌ 弹框
```

## 修复方案(diagnose 阶段产出 · 用户确认后才进 dev · 本阶段不写 fix 码)

### 方案描述
给 `terminalRegistry.ts` 里 `new Terminal({...})` 的构造选项**加一个 `linkHandler`**,把 OSC 8 链接的激活路由到与纯文本链接同一条系统浏览器路径(`window.termpro.openExternal`):

```ts
const term = new Terminal({
  allowProposedApi: true,
  // ...现有选项...
  linkHandler: {
    activate: (event, uri) => {
      event.preventDefault();
      window.termpro.openExternal(uri);
    },
    // allowNonHttpProtocols 保持默认 false:
    //   OscLinkProvider 会先校验 URL.protocol ∈ {http,https},非 http 链接直接忽略;
    //   与 main 进程 shell:open-external 的 ^https?:// 守卫一致(双重防护)。
  },
});
```

**为什么这样改是根因修复**:`linkHandler` 是 xterm 公开 `Terminal` 选项(`xterm.d.ts:163`),一旦提供,OscLinkProvider.ts:89 就走 `linkHandler.activate` 而**永不**触达 `defaultActivate`(弹框被釜底抽薪)。`openExternal` → preload → main `shell:open-external`(main.ts:101)→ `shell.openExternal` → **系统默认浏览器**,与纯文本链接完全一致。

**取舍 / 备选**:也可考虑反注册 OscLinkProvider 或调整 provider 顺序,但那是 hack(核心 provider 不可移除/重排)且无法关掉确认框语义。设 `linkHandler` 是 xterm **官方提供的定制点**,最小、最稳、语义最正。已采纳。
