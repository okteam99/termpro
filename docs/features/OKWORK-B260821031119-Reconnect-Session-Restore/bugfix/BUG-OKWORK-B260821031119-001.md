# Bug 排查报告：重连成功后残留过期的会话恢复失败提示

## 状态

---

## 问题描述

**报告人**：用户  
**报告时间**：2026-08-21  
**问题描述**：远程 Host 经断线重连后，终端底部出现：

```text
[OkWork] Could not restore this session after reconnecting: host connection lost — press any key to retry
```

**期望行为**：当更新一轮重连已经排队并成功恢复会话时，不应再向终端写入旧一轮收养的失败提示；只有最新一轮收养最终失败时才提示用户按键自愈。

**实际行为**：旧一轮收养进入最终失败回调时会立即写提示；紧随其后的更新一轮收养即使成功，只会清掉“是否已提示”的内存标记，无法撤回已写进 xterm 缓冲的文本。因此侧栏可以已经恢复为绿色/ready，终端仍显示一条已过期、误导用户继续重试的错误。

---

## 复现步骤

1. 启动同一 `hostId` 的第一轮 `readoptHostSessions`，让它停在最终 `session.attach` 尝试中。
2. 第一轮尚未落定时，模拟更新一轮 reconnect 完成，再调用一次 `readoptHostSessions`；第二轮因同 host 串行规则排在第一轮之后。
3. 让第一轮以 `host connection lost` 失败；当前实现立即调用 `notifyAdoptFailed` 写入终端提示。
4. 第二轮随即成功并执行 `reconcileBadge`，模拟 Host 已 ready 且会话已恢复。
5. 断言终端不应收到失败提示；当前实现稳定失败，实际收到截图中的完整文案。

**复现环境**：

- 基线：`origin/main`，commit `a02a11a`（v0.3.116）
- 测试：Vitest 3.2.6，jsdom
- 临时诊断反馈环：连续 3/3 次复现，单次约 0.5 秒；诊断文件已清理，正式测试在 dev 阶段落入既有测试文件

## 根因分析

### 相关代码

| 文件 | 行号 | 问题描述 |
|------|------|----------|
| `src/renderer/services/sessionReadopt.ts` | 140–146 | `inflight` 只保存 `hostId → Promise` 尾指针，没有请求代次或 superseded 状态 |
| `src/renderer/services/sessionReadopt.ts` | 198–206 | 最终尝试直接把全局 `notifyAdoptFailed` 作为回调传入，没有验证该请求是否仍为最新代次 |
| `src/renderer/services/sessionReadopt.ts` | 207–235 | 新请求只排在旧 Promise 后；排队不会作废旧请求的重试或用户提示副作用 |
| `src/renderer/terminal/terminalRegistry.ts` | 1016–1043 | 单会话 `session.attach` 失败会同步调用当前请求提供的 `onAdoptFailed` |
| `src/renderer/services/sessionReadopt.ts` | 160–170 | 失败回调把不可撤销的文字写入 xterm 缓冲 |
| `src/renderer/services/hostClient.ts` | 83–96 | transport 非 `OPEN` 时抛出截图中的 `host connection lost` |

### 根因

`readoptHostSessions` 的串行化只解决“同一 Host 两轮收养不能并发重建 Tab”，但没有表达“后到的重连收养请求取代先到请求”的代次语义。

当旧请求已在最终尝试内、更新请求又已经排队时，旧请求仍有权执行 `onAdoptFailed`。这个回调会立即把错误写进 xterm；之后更新请求成功只能通过 `reconcileBadge` 清理 `noticedTabs`，不能删除已写出的文本。于是 UI 的连接状态与终端提示出现矛盾：连接已经 ready，终端仍声称必须按键重试。

这也是 `product-overview/PENDING.md` 中 PENDING-008 已记录但未落地的“在途收养不随新代次显式作废”边缘问题。本次用户截图把它从加固项提升为已复现缺陷。

### 调用链路

```text
HostClient transport close/reconnect
  → reconnectController.onReconnected(configId)
  → readoptHostSessions(configId)
  → readoptHost()
  → session.attach
  → WebSocketTransport.send() 抛 host connection lost
  → readoptHost 调 onAdoptFailed
  → notifyAdoptFailed 写入 xterm

同时：更新一轮 readoptHostSessions(configId)
  → 仅排在旧 inflight Promise 后
  → 随后成功 reconcileBadge
  → 无法撤回旧代次已写入的终端提示
```

### 其他假设的核验

- Host 会话协议损坏：排除。`reconnectContinuity.integration.test.ts` 14 条真实 PTY/WS 测试通过，同 PID attach、断线回放、session.list 均正常。
- Sidebar 握手时序回归：排除为本次主因。生产接线测试 6 条通过，确认收养由 WebSocket 真正 open 后的 reconnect promise 驱动。
- 普通重试或 WebSocket 发送守卫错误：排除。相关 47 条测试全部通过；非 OPEN 时快速抛错是必要保护，问题在错误所属代次已过期后仍产生用户副作用。
- 隧道真实持续不稳定：仍可能产生“最新代次最终失败”的合法提示，但不能解释“更新代次已经成功后仍残留旧提示”；该场景应继续保留提示能力。

## 修复方案

### 推荐方案：每个 Host 引入 readopt generation

在 `sessionReadopt.ts` 为每个 `hostId` 记录最新请求代次：

1. 每次调用 `readoptHostSessions(hostId)` 时递增 generation；新请求仍沿用现有 Promise 串行队列，避免双重建 Tab。
2. 旧请求在每次尝试前、失败后和退避后检查自己是否仍是最新代次；若已被更新请求取代，立即停止后续重试。
3. 最终尝试的 `onAdoptFailed` 使用带 generation 的包装回调；只有当前最新代次可以调用 `notifyAdoptFailed`。这覆盖“旧请求已进入 await，期间新请求到达”的关键窗口。
4. 最新请求完成后清理 generation 记录，避免模块级 Map 泄漏。
5. 将诊断反馈环固化到 `sessionReadoptNotice.test.ts`（或同域测试文件），同时覆盖：旧代次提示被抑制、更新代次成功、真正的最新代次最终失败仍提示、不同 host 互不影响。

### 取舍

- 保留现有串行化、退避和按键自愈语义，不改 Host 协议、不取消底层 RPC。
- 旧代次已在执行中的一次 `session.attach` 无法物理中止，但其结果与用户提示会被 generation 闸门隔离；改动集中且不引入 AbortSignal 跨层契约。
- generation 属 renderer 内部生命周期状态，不需要持久化。

### 备选方案：等队列清空后再统一决定是否提示

可把失败暂存到 host 级状态，等最新队列任务完成后再输出。但这会把每个 Tab 的错误聚合、成功清理与 inflight 队列耦合起来，状态更多、时序更难验证；相比 generation 闸门没有额外收益，不推荐。

### L2 Bug 回归层

### 实现

- `sessionReadopt.ts` 增加 per-host `latestGeneration` token。
- 新请求仍排进原 `inflight` 队列，保持同 Host 不并发重建 Tab。
- 旧请求首次尝试仍执行，失败后若已被新代取代则停止重试并记录 WARN。
- 最终 `onAdoptFailed` 在写 xterm 前检查 generation；只有最新代次可以输出用户提示。
- 最新请求结束后清理 generation token，避免模块级状态泄漏。
